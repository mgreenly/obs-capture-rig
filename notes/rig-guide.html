01 · Start here

Working with this setup

The OBS side is fully scripted and reproducible. The camera side is manual and is the part that actually breaks — see section 02. Everything lives in ~/Projects/obs, tracked in git.

The scripts

apply.py
./apply.py  |  ./apply.py --write
Restores the entire OBS config — profile, encoder settings, scene collection. Dry-run by default; --write applies. Backs up first, into backups/<timestamp>/. Refuses to run while OBS is open, because OBS rewrites its config on exit and would silently undo the changes.
bin/level
./bin/level <file.mov>
Peak and RMS dBFS per channel, decoded from the actual samples. bin/probe reports the audio format, which a fully silent track satisfies just as well as a good one — this is what proves a scene captured sound. Comparing RMS against a known-good take also shows whether it came through the same path.
make probe
make probe
Runs all device probes in order. The first thing to reach for when something looks wrong.
bin/caps
./bin/caps
Every resolution / pixel format / frame rate each capture device is currently offering. The Cam Link's list reflects the live HDMI signal, so this doubles as a read on what the camera is actually sending. The HD60 X's list is static and tells you nothing about its input.
bin/sig
./bin/sig
Connection state and format count per device. Quickest before/after check when changing camera settings.
bin/adev
./bin/adev
CoreAudio input devices with the UIDs OBS stores as device_id. Used by apply.py to resolve Wave Link by name.
bin/probe
./bin/probe ~/Movies/<file>.mov
What a finished recording actually contains: resolution, frame rate, codec, color tags, audio format, effective bitrate. The only check that proves config intent survived to disk.

Asking Claude in a future session

Point at the repo first — ~/Projects/obs — then any of these work as-is:

Restore the setup

"Re-apply my OBS capture rig config from ~/Projects/obs"

Quit OBS first, or expect to be asked to. Claude should dry-run, show the diff, then write.

Something looks wrong

"Check my capture rig — run the probes in ~/Projects/obs"

Catches wrong resolution, a camera that reverted, a missing device, a Wave Link UID that changed.

Verify a recording

"Probe my latest recording in ~/Movies"

Confirms what actually landed on disk rather than what OBS was told to do.

Change the config

"Change the rig to <X> and update apply.py + the guide"

Keeps the script, this guide and the README in step so the repo stays the source of truth.

The one rule

Quit OBS before any config change. OBS holds its entire configuration in memory and writes it out on exit — edit files underneath a running OBS and your changes vanish the moment it closes. apply.py enforces this, but the same applies to hand edits.

02 · Manual — the fragile part

Sony ZV-1 walkthrough critical

No script can touch this; it is all on-camera menus. If the camera is reset, swapped, or someone changes a mode, this is what has to be redone. Symptom of it being wrong is always the same: the Cam Link reports 1080p instead of 4K, and no OBS setting can compensate.

Two traps that cost the most time

Movie mode is not the record button. The ZV-1 has a Mode button on the top plate cycling Still / Movie / S&Q. Pressing the red MOVIE record button records video but does not put the camera in Movie mode — and 4K Output Select is hidden entirely while in Still mode.

Proxy Recording silently kills HDMI. Sony's own documentation: recording 4K with proxy active means movies "will not be output to a device connected by HDMI cable." No warning appears on screen. The capture just goes dead.

1

Movie mode

Mode button (top plate) → Movie

Not the red MOVIE record button. Confirm the screen switches to movie framing. Everything below depends on this — several menu items do not exist in Still mode.

2

Region

MENU → Setup → NTSC/PAL Selector → NTSC

30p only exists in NTSC; PAL gives 25p. This restarts the camera and asks to reformat the card, so do it before anything else. Normally already correct — check only if 30p options are missing.

3

File format the usual culprit

MENU → Movie tab → File Format → XAVC S 4K

Sony's docs call this tab "Camera Settings2"; the camera labels it Movie1 / Movie2. It is not the Quality/ImageSize tab, which is stills only. This was the actual blocker when the rig was first set up — the camera was in XAVC S HD, so HDMI output was 1080p59.94 no matter what else was configured.

4

Record setting

MENU → Movie tab → Record Setting → 30p 100M

Directly below File Format. 100M over 60M for the higher internal bitrate, which matters while the card copy is being kept.

5

Proxy recording

MENU → Movie tab → Proxy Recording → Off

Usually one page across — use the right arrow to reach Movie2. Mandatory in Memory Card+HDMI mode. See the trap note above.

6

4K output select

MENU → Setup → 4K Output Select → Memory Card+HDMI

This item only appears in Movie mode with a 4K-capable device connected. If it is missing, go back to step 1 — that is almost always why. Its presence is also a useful diagnostic: it means the camera is reading the Cam Link's EDID correctly, so the cable and capture device are fine.

Alternative: HDMI Only(30p) runs cooler and has no clip length limit, at the cost of the card backup. See the trade-off below.

7

Clean feed and device control

MENU → Setup → HDMI Settings → HDMI Info. Display → Off
MENU → Setup → HDMI Settings → CTRL FOR HDMI → Off

HDMI Settings grey out while a cable is attached — unplug the HDMI cable from the camera to change these, then reconnect. Info Display Off strips focus boxes and overlays from the feed; CTRL FOR HDMI Off stops the camera reacting to HDMI-CEC chatter mid-take.

8

Power management

MENU → Setup → Power Save Start Time → Off
MENU → Setup → Auto Power OFF Temp. → High

Without these the camera sleeps or thermally cuts out mid-session and the capture goes black. The ZV-1 runs warm in 4K, and Memory Card+HDMI is the hottest-running output mode.

9

Verify before touching OBS

cd ~/Projects/obs && ./bin/sig

Look for Cam Link 4K … max: 3840x2160. If it still reads 1920x1080 the camera is sending 1080p and nothing in OBS will fix it.

Reseat the HDMI cable after any camera change — the Cam Link caches the handshake and keeps reporting stale modes until it is reconnected.

Memory Card+HDMI
Current setting

Records 4K to the card and feeds OBS, so there is a safety copy if OBS drops out. Costs thermal headroom and clip length, and Proxy Recording must be off without exception.

HDMI Only(30p)
Cooler alternative

No card recording — noticeably less heat and no clip length limit. The camera's own screen may go blank at 30p; monitoring happens in OBS instead, which for a fixed camera costs nothing.

If 4K still will not appear

In order: Movie mode (step 1, by far the most common). File Format (step 3, the actual blocker last time). The cable — the ZV-1's port is micro-HDMI Type D, and a marginal cable passes 1080p happily while failing the EDID read that tells the camera it is talking to a 4K sink. The port — move the Cam Link and confirm it still enumerates with ./bin/sig. A camera settings reset is the blunt last resort.

Keep the capture devices on separate USB buses

04 · Measured, not from spec sheets

Device capabilities

Nothing in this chain can capture 4K60

The HD60 X reaches 4K at 30 fps only; at 60 fps it drops to 1440p or 1080p. The Cam Link does 4K30 when fed 4K. This is a capture-side ceiling — the M4's media engine would encode 4K60 without effort. That is why the whole rig targets 4K30.

Cam Link 4K camera

A single mode, because the Cam Link advertises only what the ZV-1 is currently sending. Nothing to mis-select in OBS. If this list shows 1080p instead, the camera has reverted — go to section 02. Before the camera was configured it offered two 1080p59.94 modes and no 4K at all.

1920 × 1080yuvs 4:2:260, 50, 30, 25

14 modes down to 720×480 SD, published regardless of what is plugged in. This list is not a signal indicator — unlike the Cam Link's.

What 4K costs in chroma

Both devices offer 4:2:2 (yuvs) at 1080p but only 4:2:0 (420v) at 2160p, so the 4K path subsamples color more aggressively. At four times the pixel count it is still clearly the better image — but the trade is real, and it is the capture hardware imposing it, not the camera.

Frame rate is 29.97, not 30

Sony's "30p" in NTSC is really 29.97, which is why the OBS canvas is set to fractional 30000/1001 rather than the integer 30 preset. A 30.00 canvas against a 29.97 source duplicates a frame every few seconds. The HD60 X's exact 30.00 is the one absorbing the 0.1% difference — the correct choice, since a face shows it and a screen does not.

Why recordEncoder.json holds only two keys

OBS serialises only values that differ from the encoder's defaults. The file it writes is exactly:

{"bitrate":100000,"keyint_sec":1}

The absence of rate_control and profile is the proof that CBR and main are already the Apple VT HEVC defaults. apply.py writes this file verbatim rather than guessing at undocumented key names — wrong keys fail silently into defaults rather than erroring.

The source named Wave XLR is not the Wave XLR

It captures Wave Link Stream Mix — the mic after Wave Link's processing. The name is the mic sitting on the desk; the device is the finished mix. Do not "correct" it to the literal Elgato Wave XLR interface: that bypasses Wave Link entirely and loses every filter.

apply.py matches this source by type (coreaudio_input_capture), never by name, so renaming it in OBS is free. The same is true of every source here — only scene names are load-bearing.

06 · Layout

Scenes

One scene collection, Rig. That is the collection name — it is what names scenes/Rig.json — and it is unrelated to the names of the scenes inside it. Renaming a scene does not move that file; renaming the collection does.

The profile is separately named Untitled. The two are independent. apply.py reads both from user.ini [Basic] rather than hardcoding paths, and checks the names against PROFILE_NAME and COLLECTION_NAME — patching a collection OBS is not actually loading would look like it worked while changing nothing.

Every scene that should have sound needs its own audio item

An audio source is live only in the scenes that contain it, and the global Mic/Aux slot is deliberately empty — it was a second live audio path and the cause of the launch hang. Nothing else carries audio into a scene.

BigHead recorded silence until its Wave XLR item was added. Thumb is silent on purpose. When adding audio to a new scene use the existing source (Add → Audio Input Capture → Add Existing), never a new capture — a second capture of the same device is a separate source with its own settings and monitoring state.

The OBS log is the check that settles it:

- scene 'BigHead':
    - source: 'Wave XLR' (coreaudio_input_capture)
    - source: 'Sony ZV1' (macos-avcapture)

Thumb — thumbnail still

ItemPositionScale On canvasRole
Image0, 01.000 fills canvasSwapped per recording; no audio

Sony ZV1 and Wave XLR are shared, not copied

Both scenes reference the same camera capture and the same audio capture — identical source_uuid, listed twice. Changing a source's settings changes it in every scene at once, which is what makes apply.py's per-source patching safe. It also means the camera has two different roles: a PiP in Desktop, full-frame in BigHead.

Scale is relative to source pixels

A scene item's scale multiplies its source resolution, so changing a capture preset from 1080p to 4K doubles the on-screen size unless the scale is halved to compensate. apply.py handles this: when a source's preset resolution changes it rescales dependent items by the inverse ratio, preserving on-screen layout. Because the preset changes only once, re-running is idempotent — it will not keep shrinking the PiP.

Inverse scaling is only correct for an item whose on-screen size should be preserved. A full-frame item should follow the new resolution instead, so FULLSCREEN_ITEMS in apply.py lists the items that snap to scale 1.0: Desktop/HDX 60, BigHead/Sony ZV1, Thumb/Image. That list is keyed on (scene, item), not on the source — Sony ZV1 needs opposite treatment in its two scenes.

This also means apply.py leaves your manual layout tweaks alone. Resize the PiP in OBS whenever you like; the script only touches scale when a resolution actually changes underneath it.

Renaming a scene stops apply.py

Source names are free — apply.py matches sources by type. Scene names are not: FULLSCREEN_ITEMS is keyed on them. apply.py checks the scene list against SCENES up front and exits rather than apply a stale layout silently. If you rename or add a scene, update SCENES and FULLSCREEN_ITEMS in apply.py and the tables above.

07 · Control surface

Stream Deck

Stream Deck Mini — 6 keys, 3 columns × 2 rows. Key coordinates in the profile JSON are column,row.

col 0col 1 col 2
row 0DesktopThumb BigHead
row 1Record toggle— Next page

Two plugins, one on each side

The scene keys light up when their scene is live and the record key shows OBS's real recording state. That feedback is the whole reason to use the plugin rather than system hotkeys, which are fire-and-forget — after one missed press a hotkey "toggle" lies to you about whether you are recording.

It needs both halves installed:

Stream Deck side
com.elgato.obsstudio.sdPlugin
In the Stream Deck app's Plugins/. From the Elgato Marketplace.
OBS side
StreamDeckPlugin.plugin
In ~/Library/Application Support/obs-studio/plugins/, placed by the Elgato installer. Ships per-OBS-version variants; StreamDeckPluginOBS32 matches OBS 32.

They speak a private streamdeck-obs protocol on 127.0.0.1:28186 — not obs-websocket, which stays disabled and needs no password. Confirm the bridge in the OBS log:

<StreamDeck> Plugin version 5.5.4.2
<StreamDeck> [Server] Listening on '127.0.0.1:28186'.

Keys bind scenes by name

A scene key's settings are just {"scene": "Desktop", "target": "program"}. Rename a scene in OBS and its key silently stops matching — the same fragility that makes apply.py halt on scene drift. Rename in both places, or not at all.

The record key takes {"longpress": false}. Set it true to require a 3-second hold, which is worth considering if you ever stop a take by accident.

Quit Stream Deck before editing the profile

Same hazard as OBS: the app rewrites its config on exit and will silently undo hand edits. The profile lives at

~/Library/Application Support/com.elgato.StreamDeck/ProfilesV3/
  <device>.sdProfile/Profiles/<page>/manifest.json

Quit the app, edit, relaunch. A good sign the edit took: the plugin adds its own keys (e.g. isInMultiAction) to your action settings on load, which means the action resolved rather than merely parsing as JSON.

09 · Proof, not intent

Verifying

Config files and startup logs prove what OBS was told to do. Only reading back a finished recording proves what happened.

cd ~/Projects/obs
make probe                                  # devices
./bin/probe ~/Movies/<newest>.mov           # the recording
./bin/level ~/Movies/<newest>.mov           # audio levels on disk

probe and level answer different questions. probe reports the audio format — which a completely silent track satisfies exactly as well as a good one. level decodes the samples. Only the second one can tell you a scene captured sound.

Reference result — 13 s test recording

VIDEO  3840x2160  29.970 fps  codec hvc1
       ColorPrimaries / TransferFunction / YCbCrMatrix: ITU_R_709_2
       FullRangeVideo: 0
AUDIO  lpcm  48000 Hz  2 ch  24-bit
153.6 MB / 13.08 s  ->  98.5 Mbps overall

Native 4K, 29.97 matching the ZV-1, HEVC (hvc1), Rec.709 limited range, lossless 24-bit PCM, CBR landing within 1.5% of the 100 Mbps target.

From the OBS log

[VideoToolbox advanced_video_recording: 'hevc']: session created with hardware encoding
Number of lagged frames due to rendering lag/stalls: 1 (0.2%)

One lagged frame at session start is normal. Two concurrent 4K USB capture streams plus hardware HEVC sit comfortably within the M4's headroom. Watch the Stats dock (View → Docks → Stats) during long takes — rendering lag is the one failure mode that never shows up in the output file.

Reference result — audio levels

        peak dBFS   RMS dBFS
  ch0     -9.3       -30.3
  ch1     -9.3       -30.3

Both channels identical, because the Wave XLR is a mono mic duplicated to stereo by Wave Link. Aim for peaks between -12 and -6 dBFS. Comparing RMS against a known-good take is also how you confirm a new scene is carrying audio through the same path rather than some other device.

Set gain for headroom, not for level

Recording is lossless 24-bit PCM, whose noise floor sits far below anything this mic and preamp produce. Recording quieter therefore costs nothing — lifting it in post is free. Clipping is the one error that cannot be undone, so headroom is the only thing worth optimising for.

An early take here peaked at -2.8 dBFS, under 3 dB of headroom. Dropping the gain ~6 dB moved it to -9.3. Note the peak fell 6.5 dB while RMS fell only 3.7 — the original peak was a transient, not the speaking level.

Adjust the Wave XLR's analog gain knob, not the Wave Link fader. The knob is the preamp ahead of the converter; a digital fader after the A/D only makes an already-clipped signal quieter. That the peak moved with the knob is the proof the ceiling was analog. Clipguard is a backstop, not a substitute for correct gain.

Storage

Roughly 45 GB/hour at 100 Mbps. With ~842 GB free that is about 18 hours of recording. 4K masters accumulate quickly — worth a glance before a long session.

10 · Known failure modes

Troubleshooting

Cam Link shows 1080p
Camera reverted → section 02
Check Movie mode first, then File Format. Reseat the HDMI cable before trusting any reading — the Cam Link caches the handshake.
Dock icon bounces, no window
sudo killall coreaudiod
OBS's main thread blocks in AudioDeviceStart when a capture card's audio device is wedged — observed once at 2m27s before it returned on its own. Naming audio devices explicitly rather than default keeps capture-card audio out of the startup path, which is why the global Mic/Aux was removed.
Config changes vanish
OBS was running
It rewrites everything on exit. Quit first, always.
Audio sounds unprocessed
Source pointed past Wave Link
The source is named Wave XLR; check the device it actually holds. It must be Elgato Wave Link Stream Mix, not the Elgato Wave XLR interface — the latter bypasses all filtering. Run ./bin/adev and re-apply.
apply.py: "active config is profile X / collection Y"
OBS switched profile or collection
apply.py refuses to patch files OBS is not loading. Switch back in OBS (Profile / Scene Collection menus), or update PROFILE_NAME / COLLECTION_NAME in apply.py.
apply.py: "scene layout drifted"
A scene was renamed or added
Deliberate: FULLSCREEN_ITEMS is keyed on scene names, so a rename it does not know about would apply a stale layout. Update SCENES and FULLSCREEN_ITEMS in apply.py and section 06, then re-run.
Thumb scene is blank
Image file moved or deleted
The still is swapped per recording and is not managed by apply.py — a dry-run prints references a missing file. Point the Image source at the new file in OBS.
Doubled / echoing audio
OBS monitoring is on
Every source must be Monitor Off; Wave Link's Monitor Mix already feeds the headphones.
Audio clipped / distorted
Gain too hot at the preamp
Run ./bin/level; peaks near 0 dBFS confirm it. Turn the Wave XLR's analog knob down, not the Wave Link fader — see section 09.
A scene records no audio
No audio item in that scene
Audio sources are live only in scenes that contain them, and the global Mic/Aux slot is deliberately empty. Check the OBS log's Loaded scenes block — it lists every source per scene. See section 06.
Wave Link device not found
GUID regenerated
Reinstalling Wave Link mints new virtual-device GUIDs. apply.py resolves by name, so re-running it fixes this.
Camera dies mid-take
Sleep or thermal cutout
Power Save Start Time → Off, Auto Power OFF Temp. → High. Consider HDMI Only(30p), which runs cooler than Memory Card+HDMI.
Hotkeys dead in background
Input Monitoring permission
System Settings → Privacy & Security → Input Monitoring → enable OBS. Currently denied. This does not affect the Stream Deck, which drives OBS through its own plugin rather than hotkeys — it only matters for keyboard hotkeys while OBS is backgrounded.

Rebuilding the probes

bin/ is gitignored, so a fresh clone needs make all. Requires only the Swift toolchain from Xcode Command Line Tools — no dependencies, and no camera permission, since enumerating formats never opens a capture session.

Device capabilities and recording results measured on this machine. Encoder and bitrate values are choices; capture modes and probe output are observed fact.
